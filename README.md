# VK IP Hunter

Telegram-бот, который перебирает публичные IPv4 в VK Cloud и останавливается,
когда облако выдаст адрес из нужного диапазона.

Метод тот же, что и в исходном `wait-direct-ip.sh`: у облака запрашивается
**один** публичный адрес, он проверяется по CIDR — неподходящий сразу
освобождается, подходящий сохраняется.

```
запросить адрес → получить IPv4 → проверить CIDR
     ├─ не подходит → освободить → пауза 90 с → повтор
     ├─ 409 «пул пуст» → пауза 90 с → повтор (бесконечно)
     └─ подходит    → сохранить, охоту остановить
```

Ответ `409 No more IP addresses available` — не ошибка, а состояние пула:
бот ждёт и пробует снова, пока адрес не появится. Лимита попыток по
умолчанию нет.

## Где вообще есть нужные адреса

Neutron не умеет выделять адрес «из произвольного CIDR» — только из
подсети, которая существует в проекте. Поэтому целевые диапазоны имеют
смысл лишь тогда, когда в какой-то внешней сети есть подсеть с таким
CIDR.

`/networks` показывает внешние сети проекта, их пулы и прямо отвечает на
вопрос, есть ли шанс:

```
✅ internet
    ▫️ 161.104.107.0/24
    🎯 217.16.16.0/20
    🎯 5.188.140.0/22

🎯 Целевые диапазоны найдены здесь:
• internet → 217.16.16.0/20
```

Если ни в одной сети целевых диапазонов нет, бот скажет это прямо: таких
адресов проекту сейчас не выдают, и ни ожидание, ни воркеры этого не
изменят.

## Выбор подсети — если попадается «не тот пул»

Внешняя сеть состоит из нескольких подсетей, и это разные пулы адресов.
Без явного выбора Neutron отдаёт адрес оттуда, где сейчас есть свободные,
поэтому можно бесконечно получать один и тот же чужой диапазон.

`/subnets` показывает подсети сети `internet` и отмечает те, что
пересекаются с вашими целями:

```
▫️ 161.104.107.0/24 · ext-net-01
🎯 217.16.16.0/20 · ext-net-03
    пересекается с целью 217.16.16.0/21
🎯 5.188.140.0/22 · ext-net-04
```

Выбранные подсети уходят в запрос как `subnet_id` — Neutron принимает его
и при создании порта (`fixed_ips`), и при выделении floating IP. После
этого адреса приходят только оттуда.

Отмечать можно несколько: воркеры раскладываются по списку. Четыре
воркера на четыре подсети — каждый закреплён за своей; один воркер
обходит все по очереди; два на четыре — вместе покрывают все. Раскладка
видна в логе:

```
воркер 0 · подсети 217.16.16.0/20 · 217.16.19.112 · входит в 217.16.16.0/21
воркер 1 · подсети 5.188.140.0/22 · без адреса · 409 No more IP addresses available
```

Если ни одна подсеть не пересекается с целями, бот скажет это прямо:
нужных адресов в этой сети нет вообще, и ждать бесполезно.

## Параллельные воркеры

В `/settings` задаётся, сколько адресов пробовать одновременно (1–8, по
умолчанию 1). Воркеры стартуют вразнобой, каждый со своим интервалом:
четыре воркера при интервале 90 с дают попытку примерно каждые 22 с.
Найденный целевой адрес останавливает остальных; те, кто был в этот
момент в середине попытки, доводят её до конца — если их адрес тоже
оказался целевым, он сохраняется, а не выбрасывается.

Прежде чем поднимать число: каждый воркер держит свой адрес до проверки,
поэтому четыре воркера занимают до четырёх адресов сразу. Упрётесь в
квоту проекта — облако ответит `409 Quota exceeded`, и это уже не «пул
пуст»: бот отличает эти два случая и сразу пишет, что ждать бесполезно и
надо освободить выданные адреса или убавить воркеров. Выделенные адреса
могут тарифицироваться всё время, пока держатся.

## Два способа добычи адреса

Переключаются в `/settings` кнопкой «Способ».

| | Порт во внешней сети | Floating IP |
| --- | --- | --- |
| что создаётся | порт в сети `internet` | обычный floating IP |
| как опознаётся свой | по имени `<префикс>-*` | по описанию `<префикс>-*` |
| что делать с найденным | стать интерфейсом новой ВМ (`/vm`) | привязать к существующей ВМ (`/attach`) |

По умолчанию — порт во внешней сети: именно этим способом был получен
рабочий адрес `217.16.22.90`, и он намеренно отличается от обычного
создания floating IP. Если в вашем проекте нужные диапазоны выдаются
через floating IP — переключите способ, цикл ожидания там тот же.

Это не сканирование чужих адресов и не перезапуск существующей ВМ: бот
работает только с ресурсами вашего проекта через штатный OpenStack API.

## Что умеет

* Полное управление из Telegram — консоль и `tmux` больше не нужны.
* Живое сообщение статуса, которое обновляется на каждой попытке, плюс
  сводка раз в N попыток и мгновенное уведомление о находке.
* Видно, в каком аккаунте и проекте идёт работа: подпись стоит в статусе,
  в сообщении о старте и в каждой строке лога.
* Лог пишется в `data/vkiphunter.log` с ротацией по 5 МБ и читается прямо
  в чате командой `/log` — сервер для этого открывать не нужно.
* `/debug` включает подробный режим: в лог попадают запросы к VK Cloud и
  ответы API целиком. Помогает разобрать непонятную ошибку, не
  перезапуская бота.
* Проверка адреса математикой `ipaddress`, а не сравнением строк:
  `217.16.200.1` не пройдёт как «похожий на 217.16.».
* Ошибка `409 No more IP addresses available` считается штатной — цикл
  ждёт и повторяет, ничего не пересоздавая.
* Найденный адрес не освобождается никогда: ни при остановке, ни при
  ошибке создания ВМ, ни при массовой уборке.
* Удаляются только свои пробные ресурсы — порт по префиксу имени,
  floating IP по префиксу описания. Чужие бот не трогает ни при каких
  обстоятельствах, как и уже занятые.
* Мастер создания ВМ: флейвор → образ → ключ → подтверждение, с фильтрами
  по историческим параметрам (1 vCPU, 2 ГБ, Ubuntu 24.04, диск 10 ГБ).
* Правка всех параметров прямо в боте: интервал, сеть, префикс, тайм-ауты,
  лимит попыток, целевые диапазоны и исключения.
* Режим симуляции — можно пощупать бота без облачного проекта.

## Установка

```bash
git clone <repo> /opt/vkiphunter
cd /opt/vkiphunter
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m vkiphunter
```

При первом запуске бот спросит токен от [@BotFather](https://t.me/BotFather)
и сохранит его в `data/credentials.json` с правами 0600. Дальше всё
настраивается в переписке:

1. отправьте боту `/start` — первый написавший становится владельцем,
   его ID запоминается, и больше никто управлять ботом не сможет;
2. нажмите «Подключить VK Cloud» или отправьте `/connect`;
3. проще всего выбрать «Вставить openrc-файл» и прислать вывод
   `cat /root/mcs*-openrc.sh` — бот разберёт его сам и спросит только пароль.

Доступы проверяются живым запросом к API и сохраняются, только если
подошли. Сообщение с паролем бот удаляет из чата сразу после прочтения.

Кроме openrc есть ещё три способа: логин с паролем по шагам,
application credential (не зависит от смены пароля аккаунта) и режим
симуляции — потрогать бота без облачного проекта.

`.env` не нужен, но если удобнее задать что-то заранее, переменные из
`.env.example` работают: имена совпадают с OpenRC-файлом, так что
`source mcsXXXXXXXXX-openrc.sh` перед запуском тоже сработает. Заданное
в боте имеет приоритет над окружением.

## Запуск как службы

На сервере с systemd:

```bash
cp scripts/vkiphunter.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now vkiphunter
journalctl -u vkiphunter -f
```

Где systemd нет (Termux/proot) — свой супервизор: бот переживает
закрытие терминала, `Ctrl+C` и собственные падения, перезапускаясь
через 5 секунд.

```bash
./scripts/vkiphunterctl start
./scripts/vkiphunterctl status
./scripts/vkiphunterctl logs
./scripts/vkiphunterctl stop
```

Если бот падает сразу после старта пять раз подряд, супервизор
останавливается и пишет об этом в лог — чтобы не крутить бесконечный
цикл на сломанной конфигурации. Пропавшая сеть падением не считается:
бот ждёт Telegram с нарастающей паузой и поднимается сам, когда связь
вернётся.

## Целевые диапазоны

По умолчанию — те же, что в исходном watcher-скрипте:

```
5.188.140.0/22
217.16.16.0/21
217.16.24.0/22
217.16.28.0/22
```

Три сети `217.16.*` вместе покрывают `217.16.16.0/20`, куда входил рабочий
адрес `217.16.22.90`. Списки правятся в `/targets`; исключения приоритетнее
целей, так что отбракованный подсегмент можно вырезать, не трогая цель.

## Что бот не делает

Попадание в CIDR — только предварительный фильтр. Он **не** доказывает, что
мобильный оператор пропускает адрес. Реальная проверка остаётся ручной:

1. подключить найденный порт к ВМ;
2. открыть нужный порт в security group и в firewall самой машины;
3. поднять health-endpoint и убедиться, что он отвечает из обычного интернета;
4. на телефоне выключить Wi-Fi и повторить запрос через целевую SIM/APN.

| Обычный интернет | Ограниченная сеть | Вывод |
| --- | --- | --- |
| не работает | не работает | чинить сервер, firewall или security group |
| работает | не работает | адрес не проходит белый список оператора |
| работает | работает | адрес — рабочий кандидат для этой SIM/APN на момент теста |

`whois`, ASN, PTR и принадлежность облаку сетевой тест не заменяют.

## Ограничения

* Нужный пул может больше не участвовать в новых выдачах.
* Один и тот же адрес может выдаваться повторно — счётчик в `/ips` это покажет.
* `409` может держаться долго; это состояние пула, а не поломка проекта.
* VK Cloud может изменить имя внешней сети, квоты или правила подключения
  прямого внешнего порта — имя сети меняется в `/settings`.
* Созданные порты и ВМ влияют на квоты и тарификацию.
* После перезапуска бота охота не возобновляется сама — он об этом напишет.

## Разработка

```bash
.venv/bin/pip install pytest pytest-asyncio
.venv/bin/python -m pytest
```

Тесты гоняют движок на сценарном облаке и весь бот целиком на замоканном
Telegram API — сеть при этом не используется.

```
vkiphunter/
├── cidr.py          проверка адреса по CIDR
├── state.py         настройки, статистика, найденные порты (JSON на диске)
├── secrets.py       токен и доступы к облаку (0600)
├── hunter.py        цикл охоты
├── config.py        переменные окружения / OpenRC
├── cloud/           openstacksdk, симулятор и прокси со сменой кредов
└── bot/             aiogram: хендлеры, мастер подключения, уведомления
```
